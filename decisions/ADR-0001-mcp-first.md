# ADR-0001: اعتماد MCP كواجهة أساسية

## الحالة

مقبول مبدئيًا.

## السياق

Resource Studio يحتاج إلى واجهة رسومية حديثة، CLI للأتمتة، وتكامل مع عملاء الذكاء الاصطناعي. بناء منطق مستقل لكل قناة يسبب اختلافًا في النتائج ويجعل التوسع مكلفًا. MCP يوفر عقدًا قياسيًا لاكتشاف الأدوات والموارد واستدعائها، لكن أدوات تعديل الملفات تحمل خطرًا أعلى من أدوات القراءة.

## القرار

نعتمد **MCP-first architecture** وفق المبادئ التالية:

1. النواة واحدة، وتستدعيها الواجهة وCLI وMCP.
2. أدوات MCP تُقسم إلى قراءة وتخطيط وتعديل.
3. النقل المحلي `stdio` هو الافتراضي.
4. النقل البعيد يؤجل حتى اكتمال المصادقة والتدقيق والحماية من SSRF وconfused deputy.
5. التعديل لا يعمل على الأصل، بل على workspace معزول وبعد خطة وتأكيد بشري.
6. كل أداة تعيد structured output ثابتًا وaudit URI.
7. أدوات Resource Studio وإصدارها الداخلي منفصلان عن إصدار بروتوكول MCP.
8. لا تُضمّن أو تُعدّل أو تُعاد توزيع مواد خارجية مملوكة داخل مشروع Resource Studio.

## البدائل المرفوضة

### إضافة MCP في نهاية المشروع

مرفوضة لأنها ستفرض إعادة تصميم الواجهة والنواة بعد اكتمالها، وقد تنتج أداة MCP مختلفة السلوك عن UI وCLI.

### جعل MCP ينفذ أوامر عامة

مرفوض لأنه يفتح مسارًا لتجاوز سياسات المسارات والتنفيذ، ولا يوفر schema واضحًا ولا تدقيقًا كافيًا.

### اعتماد النقل البعيد منذ البداية

مؤجل لأن الاستخدام الأول محلي ويتعامل مع ملفات المستخدم. البدء عن بعد يضيف OAuth وإدارة جلسات وشبكة إلى مساحة لا تحتاجها المرحلة الأولى.

## النتائج

يزداد الاستثمار في تصميم العقد والاختبارات مبكرًا، لكننا نحصل على قابلية توسع أفضل، وإمكانية استخدام Resource Studio عبر UI وCLI وMCP دون اختلاف في المنطق، وحاجز أمان واضح قبل عمليات التعديل.

## المراجعة

يُراجع هذا القرار بعد اكتمال مرحلة MCP القراءة فقط، وقبل تفعيل Streamable HTTP أو إضافة plugins ذات صلاحيات كتابة.
