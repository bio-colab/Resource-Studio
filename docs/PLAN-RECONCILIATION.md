# فض التعارضات وخطة التنفيذ المعتمدة

**التاريخ:** 2026-08-20  
**المرجع:** `pasted_content.txt` المرفق من المستخدم  
**الحالة:** معتمد للتنفيذ المرحلي

## 1. قراءة الخطة

الخطة المرفقة لا تقترح ميزة واحدة، بل تصف منصة كاملة لتحرير موارد PE: نواة تحليل وكتابة، نظام مشروع، Undo/Redo، محررات مرئية، تعريب، Diff/Merge، CLI، إضافات، سكربتات، واجهة حديثة، تحقق، تقارير، Git-friendly export، Build Pipeline، MUI، .NET resources، وMSIX/PRI.

القيمة الأساسية في الخطة هي العبارة التالية:

> **Resource editing as a safe, scriptable, plugin-driven project system**

سنعتمد هذه العبارة كمعيار تصميم، لكننا لن ننفذ جميع الأجزاء بالتوازي؛ لأن الكتابة الثنائية ومحررات Dialog والإضافات المعزولة تعتمد على نواة مشروع وserializer واختبارات لم تُبنَ بعد.

## 2. التعارضات المكتشفة والقرار الأفضل

| التعارض | الخطر | القرار المعتمد |
|---|---|---|
| إعادة بناء Resource Hacker مقابل الحفاظ على الأصل والترخيص | احتمال نسخ أو توزيع برنامج مملوك | Resource Studio مستقل، والأصل يبقى adapter محليًا اختياريًا ولا يدخل حزمة التوزيع |
| MCP في الخطة السابقة مقابل طلب المستخدم الحالي | تشتت التنفيذ وتغيير العقد أثناء بناء النواة | MCP متوقف مؤقتًا؛ لا تطوير جديد له في هذه الدورة، ولا يُحذف الكود الموثق |
| patch مساوي الحجم مقابل محرر موارد حقيقي | لا يدعم add/delete/resize وقد يخلق ثقة زائفة | استخدامه كاختبار backend فقط، ومنع اعتباره writer نهائيًا |
| البدء بـ Dialog designer مقابل String/Version/Manifest | Dialog يحتاج parser/serializer ومعاينة واختبارات أكثر | البدء بالمحررات النصية والصغيرة، وتأجيل Dialog المرئي حتى يثبت round-trip |
| Native ABI وWASM و.NET معًا منذ البداية | تضخم API وسطح صلاحيات وصعوبة debug | plugin API قراءة فقط أولًا، ثم out-of-process JSON-lines، ثم WASM/native بعد إثبات الحاجة |
| WPF وWinUI 3 وQt دفعة واحدة | ربط النواة بتقنيات واجهة متعارضة | النواة مستقلة؛ قرار UI لاحق، وWPF هو الخيار الأولي العملي لـ Windows إن بدأنا واجهة مكتبية |
| دعم PRI/MSIX داخل `.rsrc` | نموذجان مختلفان للموارد والحزم | وحدة منفصلة مؤجلة بعد PE/Win32 |
| Scripting Python/Lua/JS/.NET مبكرًا | تنفيذ كود غير موثوق وصعوبة الصلاحيات | يؤجل حتى يستقر plugin SDK، ويبدأ بـ dry-run وقراءة فقط |
| تعديل ملفات موقعة أو تجاوز الحماية | فقدان الثقة أو إساءة الاستخدام | كشف التوقيع والتحذير فقط؛ إعادة التوقيع اختيارية بملكية المستخدم لشهادته |

## 3. ترتيب الأولويات

الأولوية ليست لعدد الميزات، بل لتقليل احتمال تلف الملف وخلق API يمكن أن تعيش عليه الإضافات. لذلك ترتيبنا هو: نظام المشروع، النموذج الداخلي، writer موثوق، الأوامر والتراجع، الفهرسة والصحة، ثم المحررات ذات أعلى قيمة، وبعدها الإضافات والترجمة والأتمتة.

| الأولوية | المجموعة | سبب التقديم |
|---:|---|---|
| P0 | Project/Workspace/Snapshot/Backup | تمنع الكتابة الخطرة وتتيح التراجع |
| P0 | Resource model/index/health | أساس كل محرر ومقارنة وإضافة |
| P0 | Command/Undo/Redo | يمنع ربط كل زر بكتابة مباشرة |
| P1 | Real PE resource writer | شرط التحرير الحقيقي |
| P1 | String/Version/Manifest/Raw editors | أعلى قيمة وأقل تعقيد من Dialog |
| P1 | Localization + Diff | جوهر استخدام التعريب والمقارنة |
| P2 | Plugin manifest/permissions/registry | يجعل المنصة قابلة للتوسع بعد ثبات النواة |
| P2 | CLI/Build/Reports/Git export | يحولها إلى أداة إنتاجية قابلة للأتمتة |
| P3 | Dialog/Menu/Icon visual editors | يحتاج serializers ومعاينات واختبارات أعمق |
| P3 | PE inspector/MUI/.NET | توسع تحليلي بعد ثبات الموارد |
| P4 | MSIX/PRI/Scripting/Remote MCP | وحدات منفصلة ذات مخاطر وتبعيات إضافية |

## 4. ما سيُعتبر إضافة فعلية

في هذه الدورة لا نعدل `ResourceHacker.exe` نفسه. الإضافة الفعلية ستكون Resource Studio ومكوناته الخارجية: نواة مشروع، محررات، أدوات مقارنة، backend موارد، plugin host، وقوالب وتقارير. يمكن استخدام نسخة العمل الحالية كمرجع واختبار ومحول محلي أثناء التطوير، لكن لا تُضمّن في الإصدار الموزع قبل مراجعة الترخيص.

## 5. تعريف الإنجاز

لا تعتبر المهمة مكتملة لأنها تعمل مرة واحدة. يجب أن يكون لها عقد واضح، اختبار نجاح وفشل، round-trip عند الكتابة، سجل عملية، وقياس يثبت أن الأصل لم يتغير. إذا تعارضت السرعة مع سلامة الملف، نختار السلامة ونؤجل الميزة.
