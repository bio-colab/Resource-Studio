# تدقيق TODO المعماري والوظيفي — 2026-08-20

## الحكم المختصر

الخطة الحالية قوية جدًا في **نواة تحرير الموارد**: المشروع المعزول، Save As، snapshots، Undo/Redo، LIEF، parsers/serializers الأساسية، التعريب، المقارنة، CLI، التقارير، والإضافات المعزولة. لكنها ليست «مكتملة لكل ما يمكن تغطيته» بعد؛ إذ ينقصها عدد من القدرات التي لا تضيف محررًا جديدًا فقط، بل تغيّر مستوى **السلامة والاعتمادية وقابلية الاستخدام الإنتاجي** للمنصة.

أعلى فجوتين هما **ضمان أن التغيير اقتصر على الموارد المقصودة** و**دورة حياة Authenticode الكاملة**. أما أهم فجوة أمنية في التصميم فهي أن الإضافة خارج العملية تحتاج حدود موارد وصلاحيات تشغيلية حقيقية، لا مجرد timeout وpermission gate. هذه الفجوات أضيفت إلى `TODO.md` تحت المعرّفات `GAP-01` إلى `GAP-12`.

## الفجوات التي قد تحدث فرقًا كبيرًا

### 1. ضمان التغيير الجراحي — `GAP-01`

نجاح LIEF في كتابة ملف PE وإعادة فتحه لا يثبت وحده أن التغيير اقتصر على المورد المطلوب. المنصة تحتاج baseline قبل التعديل وبعده يقارن sections وimports وexports وrelocations وTLS وdebug وoverlay وdata directories، ثم يرفض أو يرفع تحذيرًا عند تغير جزء غير مصرح به. هذه الوظيفة أهم من إضافة محرر ثانوي، لأنها تمنع تلفًا صامتًا في ملفات حساسة.

توثّق LIEF أن الموارد تمثل شجرة مستقلة، وأنها غالبًا توجد في `.rsrc` لكن ذلك ليس قاعدة مطلقة؛ لذلك يجب ألا يُبنى التحقق على اسم section فقط [1].

### 2. دورة Authenticode كاملة — `GAP-02`

الخطة الحالية تكشف وجود التوقيع وتحذر من تغير الهاش، لكنها تحتاج مسارًا واضحًا: قراءة الشهادة، authentihash، الخوارزمية، timestamp، نتيجة التحقق، سبب بطلان التوقيع بعد التعديل، وخيار strip صريح، ثم تكامل إعادة توقيع خارجي على Windows دون تضمين أداة مملوكة أو تخزين مفاتيح داخل Resource Studio. توفّر LIEF واجهات authentihash و`verify_signature` و`cert_dir` و`signatures`، ما يجعل جزءًا من ذلك قابلًا للتحقيق في طبقة القراءة [2].

### 3. خطة معاينة قبل الكتابة — `GAP-04`

ينقص المنصة مفهوم transaction plan مستقل عن التنفيذ. قبل الحفظ ينبغي للمستخدم أو CLI رؤية: المورد المتأثر، الحجم قبل/بعد، اللغات، hash قبل/بعد، التأثير على التوقيع، output المقترح، backup، والتحذيرات. هذا يحول الحفظ من عملية غير قابلة للمراجعة إلى عملية قابلة للموافقة والتدقيق، ويمثل أساسًا جيدًا لأي UI أو MCP مستقبلي دون تطوير MCP الآن.

### 4. حدود الإضافات الحقيقية — `GAP-06`

الصلاحيات المعلنة وtimeout وquarantine مهمة، لكنها لا تكفي كـ sandbox. ينبغي تحديد حجم المدخل، الزمن، CPU، الذاكرة، عدد العمليات، filesystem المسموح، وحالة الشبكة الافتراضية، مع تنظيف temp files. هذه أولوية حرجة لأن الإضافة هي الكود الوحيد المقصود أن يأتي من خارج النواة.

### 5. توافق PE على شكل profiles — `GAP-03` و`GAP-11`

ينبغي تحويل عبارة «يدعم PE» إلى مصفوفة profiles: PE32، PE32+، EXE، DLL، SYS، named resources، overlay، signed files، ARM64X، delay imports، exceptions، load-config، CLR، وملفات ذات resource tree غير اعتيادية. توثيق LIEF يذكر أن parsing بعض المكونات مثل exceptions وARM64X وsignature قابل للضبط عبر `ParserConfig`، لذلك يجب أن تسجل Resource Studio إعدادات parser المستخدمة ولا تفترض أن عدم ظهور المعلومة يعني عدم وجودها [2].

### 6. قفل المشروع والتعافي من الانقطاع — `GAP-05`

الـ snapshot والـ backup يعالجان الاسترجاع اليدوي، لكن لا يوجد بعد lockfile يمنع تشغيل مشروع واحد من عمليتين، ولا journal واضح للمعاملة. هذه وظيفة صغيرة نسبيًا وعالية الأثر، خصوصًا عندما يبدأ CLI أو UI أو batch automation في العمل على ملفات كبيرة.

### 7. بحث موحد فعلي — `GAP-07`

يوجد بحث في HexViewer، لكن تجربة الأداة تحتاج بحثًا واحدًا عبر type/name/language، النصوص ASCII وUTF-16، regex، bytes، وresource payloads، مع نتيجة تحتوي resource key وoffset وpreview وتفتح المحرر المناسب. هذا من أكثر التحسينات التي سيشعر بها المستخدم يوميًا.

### 8. تغطية الموارد الأقل شيوعًا — `GAP-08`

Dialog هو النقص الأكبر، لكن Accelerator وFont وMessageTable وCursor raw وFontDir مهمة أيضًا. التوصية ليست بناء كل محرر مرئي دفعة واحدة؛ بل البدء بنماذج binary parser/serializer واختبارات round-trip، ثم واجهة Dialog لاحقًا. هذا يحافظ على قرار `DEC-06` بدل تحويل المشروع إلى واجهة ضخمة مبكرًا.

## فجوات مهمة لكنها ليست أولوية أولى

| المعرّف | الوظيفة | سبب تأجيلها النسبي |
|---|---|---|
| `GAP-09` | XLIFF/PO/RESX | مفيدة للترجمة المؤسسية، لكنها لا تعالج سلامة PE الأساسية |
| `GAP-10` | provenance/SBOM/reproducible metadata | مهمة للتوزيع والتدقيق، وتأتي بعد تثبيت writer وrelease pipeline |
| `GAP-12` | batch CLI بمعاملات قابلة للاستئناف | مفيدة للأتمتة، ويمكن بناؤها فوق transaction plan والقفل |
| UI-03/UI-04 | command palette وaccessibility وdashboard | لا ينبغي تنفيذها قبل تثبيت النواة وواجهات الاستخدام |
| PRI/MSIX | موارد حديثة | تحتاج backend ونموذجًا منفصلًا، ولا ينبغي خلطها مع `.rsrc`؛ وهذا متسق مع الخطة الحالية |

## ما لا أوصي بإضافته الآن

لا أوصي بإضافة محرر شامل لكل PE headers أو disassembler أو malware analysis أو packer/unpacker إلى Resource Studio. هذه مشاريع مختلفة في النطاق والمخاطر، وستحوّل المنصة من محرر موارد آمن إلى أداة reverse engineering عامة. كما لا أوصي بإضافة أدوات تنفيذ خارجية إلى النواة؛ تبقى النواة محلية ومحددة وقابلة للتدقيق.

## الخلاصة

الخطة الحالية **متكاملة كنواة أولى لمنصة تحرير موارد PE**، لكنها ليست شاملة لكل القدرات الإنتاجية الممكنة. لا يوجد نقص مفاهيمي يهدد الاتجاه العام، لكن توجد فجوات عالية الأثر في ضمان عدم التغيير الجانبي، التوقيع، المعاينة قبل الكتابة، sandbox الإضافات، القفل والتعافي، ومصفوفة توافق PE. أُضيفت هذه الفجوات كمهام مستقلة قابلة للتتبع، مع إبقاء التوسعات الثانوية منفصلة حتى لا يتحول المشروع إلى إعادة بناء شاملة غير قابلة للصيانة.
